# steam_api64.dll for Wine, on Kettle

Our own `steam_api64.dll`: a Steam game started under Wine without Windows Steam loads it in place
of Valve's, and Steam is reached through [Kettle](https://github.com/TheSTouch/kettle), which signs
in as the player and has Steam sign the game's ownership ticket. It is not a Steam emulator: with
no sign-in, a refused one, or an account that does not own the game, `SteamAPI_Init` fails and the
game is told there is no Steam.

```sh
./port steam signin                  # once: QR code in the terminal (or ./port steam signin <account>)
./port steam check satisfactory      # sign-in and license through the DLL, without the game
./port run satisfactory --kettle     # the game, no Windows Steam (or launch = "kettle" in its file)
```

## How it fits together

| Part | What | Built by |
|---|---|---|
| `pe/steam_api.c` | the Windows side: exports, interface objects and their vtables, callbacks, the call log | Zig (`x86_64-windows-gnu`) |
| `pe/bridge.c` | the methods that answer for real, through the Mac side | Zig |
| `pe/vtables.h`, `pe/slots.h` | every interface version's vtable (MSVC order, return kinds), generated by `gen_vtables.py` from the Steamworks SDK 1.57 headers | `python3 steam_api/gen_vtables.py --fetch` |
| `unix/bridge.m` | the Mac side, a Wine unixlib: sign-in, license check, callbacks in the Windows layout | Xcode clang, `-arch x86_64` |
| `recompsteam/` | the Steamworks answers of Mac To iOS Recomp's Steam runtime, copied unchanged | linked into the Mac side |
| `../vendor/kettle` | Kettle's Steam client core (session, sign-in, tickets), a submodule at a tag | linked into the Mac side |
| `signin/steam-signin.m` | `./port steam signin`, native on the Mac | Xcode clang |
| `check/steam-check.c` | `./port steam check`: loads the DLL as a game does and calls a few methods | Zig |
| `bridge.h` | the calls between the two sides | |

`./port` builds everything into `runtime/steam-api/` (`portkit/kettle.py`). The DLL carries Wine's
builtin signature and lives in `runtime/steam-api/bridge/x86_64-windows/`, its Mac side in
`x86_64-unix/` beside it; a run adds that folder to `WINEDLLPATH` and sets
`WINEDLLOVERRIDES=steam_api64=b`. Wine then puts our builtin in place of the game's own
`steam_api64.dll` when the game loads it; the game's folder is never changed. The whole Wine process
runs as x86-64 under Rosetta, so the Mac side is an x86-64 library too.

The sign-in is the Keychain item Kettle keeps on macOS (`Recomp Steam` / `steam-client-token`), one
for every game on the Mac. Steam lists it as "Porting Kit on *Mac*" (the sign-in) and the game's
logon as "Porting Kit: *game* on *Mac*".

## What a game gets

Real: `SteamAPI_Init` (logon and license), callbacks and call results, `ISteamUser` (SteamID,
logged on, auth session and encrypted app tickets), `ISteamApps` (ownership from the signed ticket,
DLC, install folder, build id), `ISteamUtils` (app id, Steam's time, call results) and the player's
own name in `ISteamFriends`. Everything else answers "nothing" and is logged at its first call:
cloud saves, achievements and stats, networking, matchmaking, game servers, Steam Input. What
Satisfactory asks for is in [satisfactory-interfaces.md](satisfactory-interfaces.md).

A run's `steam_api.log` (next to its `wine.log`) lists every interface handed out and every method
called; Kettle's own lines (`[recomp] steam: ...`) go to `wine.log`. `./port steam inventory <game>`
runs a game with the inventory build instead: no Steam at all, only the log.
